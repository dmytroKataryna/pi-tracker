Бінарні дані: порядок байтів, розбір пакетів, strict aliasing
(Питання як на співбесіді, нижче відповідь. Усі приклади перевірено: Mac clang ARM64 і Linux GCC 13 aarch64, листопад 2026)

Коротка відповідь на співбесіді (30 секунд): «Як ви розбираєте бінарний пакет?»
    Порядок байтів визначає протокол, а не процесор, тому кожне поле читаю окремо за його зміщенням,
    збираючи число зсувами: b[0] | b[1] << 8 для little-endian. Це працює на будь-якому процесорі,
    а компілятор сам перетворює це на одну інструкцію читання. float — зібрати uint32_t і std::bit_cast.
    reinterpret_cast на буфер чи структуру поверх буфера не роблю: порядок байтів, вирівнювання,
    strict aliasing і padding. Перед розбором перевіряю довжину, контрольну суму, а функції читання
    покриваю тестами з відомими байтами (межі: 0x8000 = -32768, 0x7FFF = 32767).

1. Що таке порядок байтів (endianness)?
    Число більше за один байт треба розкласти в пам'яті або в пакеті на кілька байтів. Порядок — яким іде перший.
    Little-endian: молодший байт першим. Big-endian: старший байт першим (як ми пишемо числа на папері).
    0x12345678 у пам'яті:
        little-endian: 78 56 34 12   ← так на x86, на ARM у Linux/macOS (перевірено на Mac і Pi)
        big-endian:    12 34 56 78   ← «мережевий порядок» (заголовки TCP/IP)
    Аналогія: дата 2026-11-18 (від старшого до молодшого, big-endian) і 18.11.2026 (від молодшого, little-endian).
    Ті самі числа, але якщо не знати формат, 03.04 прочитаєш як 4 березня замість 3 квітня.

2. Хто визначає порядок байтів: процесор чи протокол?
    Для даних у пакеті чи регістрі датчика — ПРОТОКОЛ або документація пристрою. Процесор тут ні до чого.
        MAVLink, MSP, UBX (u-blox GPS) — little-endian.
        Заголовки TCP/IP, мій кадр із сесії 3 (довжина 4 байти) — big-endian.
        Багато I2C-датчиків віддають 16-бітне значення двома регістрами: спершу старший (..._H), потім молодший (..._L) — big-endian.
    Відповідь «залежить від системи» на співбесіді — помилка. Від системи залежить лише те, як процесор
    зберігає числа у СВОЇЙ пам'яті, і правильний код від цього не залежить (див. питання 3).

3. Як прочитати int16 little-endian з буфера? Наприклад, байти 0x38 0xFF.
    Молодший байт першим: число = 0x38 | (0xFF << 8) = 0xFF38 = 65336 без знака.
    Як int16: старший біт 1 → від'ємне, 65336 - 65536 = -200.
        std::int16_t readI16Le(std::span<const std::uint8_t> bytes, std::size_t offset) {
          const auto raw = static_cast<std::uint16_t>(bytes[offset] | (bytes[offset + 1] << 8));
          return static_cast<std::int16_t>(raw); // з C++20 гарантовано: 0xFF38 → -200
        }
    Чому працює на будь-якому процесорі: << 8 — це операція над ЗНАЧЕННЯМ («помножити на 256»),
    а не над тим, як байти лежать у пам'яті.
    Чому спершу uint16_t, а потім int16_t: збираємо біти без знака, а потім кажемо «тепер це знакове».
    До C++20 перетворення 65336 → int16 було implementation-defined, з C++20 стандарт гарантує -200 (доповнювальний код).
    Перевірені межі: 00 80 → -32768, FF 7F → 32767, 38 FF → -200.
    Kotlin: ByteBuffer.wrap(bytes).order(ByteOrder.LITTLE_ENDIAN).getShort(offset)
            або вручну (b[0].toInt() and 0xFF) or (b[1].toInt() shl 8) — and 0xFF, бо Byte у Kotlin знаковий.
    У C++ uint8_t беззнаковий, тож and 0xFF не потрібен.

4. Як прочитати uint32 — little-endian і big-endian?
        std::uint32_t readU32Le(const std::uint8_t *b) {
          return static_cast<std::uint32_t>(b[0]) | (static_cast<std::uint32_t>(b[1]) << 8) |
                 (static_cast<std::uint32_t>(b[2]) << 16) | (static_cast<std::uint32_t>(b[3]) << 24);
        }
        std::uint32_t readU32Be(const std::uint8_t *b) {
          return (static_cast<std::uint32_t>(b[0]) << 24) | (static_cast<std::uint32_t>(b[1]) << 16) |
                 (static_cast<std::uint32_t>(b[2]) << 8) | static_cast<std::uint32_t>(b[3]);
        }
    int32: те саме, а потім static_cast<std::int32_t>(raw).
    Навіщо static_cast<std::uint32_t> перед кожним зсувом: uint8_t у виразі автоматично стає int (integer promotion).
        - Результат b[0] | (b[1] << 8) | ... має тип int, і присвоєння в uint32_t дає попередження
          -Wsign-conversion (перевірено, clang) → з -Werror збірка падає.
        - Для 64-бітних чисел без приведення це UB: b[4] << 32 зсуває 32-бітний int на 32 —
          clang попереджає "shift count >= width of type", UBSan: "shift exponent 32 is too large for 32-bit type 'int'",
          а результат неправильний (перевірено: замість 0x0000000100000001 вийшло 0x0000000000000001).

5. Як прочитати float?
    Зібрати 4 байти в uint32_t зсувами (питання 4), потім перетворити біти на float:
        const std::uint32_t raw = readU32Le(b);
        const float value = std::bit_cast<float>(raw); // C++20, <bit>
    Без C++20: float value; std::memcpy(&value, &raw, sizeof value);
    Перевірено: 00 00 80 3F → 1.0f.
    Припущення: float — це IEEE 754, 4 байти. На всіх реальних цільових платформах (x86, ARM) так і є.

6. Що не так із *reinterpret_cast<const std::int16_t*>(&bytes[offset])?
    Три проблеми, і кожна окремо робить код неправильним:
    1) Порядок байтів процесора. Читається так, як зберігає процесор. На x86/ARM це випадково little-endian,
       тож для MAVLink «працює», а для big-endian протоколу — неправильно на будь-якому процесорі.
    2) Вирівнювання. int16 має лежати на адресі, кратній 2, int32 — кратній 4. &bytes[1] — непарна адреса.
       На частині процесорів (Cortex-M0, старі ARM) — апаратний збій. На x86 і ARM64 зазвичай «працює», але це UB.
       UBSan ловить (перевірено на обох платформах):
           runtime error: load of misaligned address 0x... for type 'const int16_t', which requires 2 byte alignment
    3) Strict aliasing (питання 7). Масив uint8_t не можна читати через вказівник на int16_t — UB,
       і з -O2 оптимізатор має право на цьому зламати код.
    Правильно: зсуви (питання 3–4), для float — std::bit_cast або memcpy (питання 5).

7. Що таке strict aliasing і чому компілятор через нього «ламає» код?
    Правило: до об'єкта можна звертатися лише через його власний тип (або його signed/unsigned варіант).
    Єдиний виняток — будь-який об'єкт можна читати як char, unsigned char або std::byte.
    Виняток діє в один бік: int можна читати як байти, а масив байтів як int — ні.
    Навіщо це компілятору: якщо int* і float* за правилами не можуть вказувати на ту саму пам'ять,
    запис через float* не змінює те, що лежить за int*, тож значення можна не перечитувати з пам'яті.
    Демонстрація (перевірено, clang і GCC 13 однаково):
        int store(std::int32_t *i, float *f) { *i = 1; *f = 0.0f; return *i; }
        std::int32_t value = 0;
        store(&value, reinterpret_cast<float *>(&value));
        -O0: повертає 0 (чесно перечитав пам'ять після запису 0.0f)
        -O2: повертає 1, хоча в пам'яті вже 0 — компілятор «знає», що *f не міг змінити *i
    Це той самий клас помилок, що й while (!stopRequested) без atomic у День 17: з -O0 працює, з -O2 ні,
    бо оптимізатор вважає, що UB у програмі немає.
    У Java такої проблеми немає: JVM не дає подивитися на пам'ять об'єкта як на інший тип.
    ByteBuffer.getFloat() усередині робить те саме, що memcpy + порядок байтів.

8. Як тоді законно подивитися на байти як на інший тип (type punning)?
    - std::bit_cast<To>(from) (C++20): копія бітів, розміри мають збігатися. Найчистіший спосіб.
    - std::memcpy(&dst, src, sizeof dst): працює в будь-якому стандарті; компілятор прибирає виклик,
      це не повільно.
    - Читати через unsigned char* / std::byte* — дозволено (виняток із питання 7).
    - union { float f; std::uint32_t u; }: записати f, прочитати u — у C дозволено, у C++ це UB.
      GCC і clang на практиці підтримують, але на співбесіді правильна відповідь — bit_cast або memcpy.

9. Чому не накласти структуру на буфер: reinterpret_cast<const Packet*>(buffer) з #pragma pack?
    Так часто роблять у старому embedded-коді, і роками «працює». Проблеми:
    - Padding: компілятор вирівнює поля.
          struct Padded { std::uint8_t a; std::uint32_t b; };  // sizeof = 8, а не 5 (перевірено)
      #pragma pack(1) прибирає padding (sizeof = 5), але це розширення компілятора, а не стандарт C++.
    - Вирівнювання: поле b у packed-структурі лежить на непарній адресі — питання 6, пункт 2.
    - Порядок байтів: поля читаються в порядку процесора — питання 6, пункт 1.
    - Strict aliasing: буфер байтів через Packet* — питання 7.
    memcpy у packed-структуру прибирає проблеми вирівнювання й aliasing, але НЕ порядок байтів.
    Надійно: розбирати поле за полем за зміщеннями з документації протоколу (readI16Le(payload, 4) тощо).

10. Що таке мережевий порядок байтів і навіщо htons?
    Мережевий порядок = big-endian. Порт і адреса в sockaddr_in мають лежати саме так.
    htons — host to network short (16 біт), htonl — long (32 біти), назад — ntohs, ntohl.
    На big-endian процесорі вони нічого не роблять, на little-endian переставляють байти.
    Класичний баг — забути htons: 8080 = 0x1F90, без перестановки ядро побачить 0x901F = 36895,
    і сервер слухає не той порт (перевірено).
    У connectLoopback (tests/tcp_io_test.cpp): htonl(INADDR_LOOPBACK), а для порту 0 htons не потрібен — 0 в будь-якому порядку 0.

11. char знаковий чи беззнаковий?
    Залежить від платформи — стандарт це не фіксує. Перевірено:
        Mac (Apple ARM64):  char знаковий,    байт 0xC8 як int = -56
        Pi / Linux aarch64: char беззнаковий, байт 0xC8 як int = 200
    Тобто той самий код читання з char buf[] дає різні числа на Mac і на Pi.
    Висновок: для бінарних даних — лише std::uint8_t або std::byte, ніколи char.

12. Які стандартні засоби є для цього в сучасному C++?
    std::endian (C++20, <bit>)          — порядок байтів процесора: std::endian::native == std::endian::little
    std::bit_cast (C++20, <bit>)        — безпечно перетворити біти: uint32_t → float
    std::byteswap (C++23, <bit>)        — переставити байти: 0x12345678 → 0x78563412 (є на Mac clang і GCC 13)
    htons/htonl/ntohs/ntohl (POSIX)     — мережевий порядок (big-endian)
    le16toh, be32toh (<endian.h>)       — лише Linux; на Mac такого файлу немає (перевірено),
                                          там OSSwapLittleToHostInt16 з <libkern/OSByteOrder.h> → не переносно
    Boost.Endian                        — load_little_s16, типи little_int16_buf_t тощо
    Згенерований код                    — бібліотека MAVLink (mavlink_msg_*_decode), Protobuf, FlatBuffers
    На практиці найчастіше: кілька власних маленьких функцій readU16Le/readI32Le, написаних один раз
    і покритих тестами (як у src/mavlink.cpp). На роботі для MAVLink, найпевніше, буде згенерована бібліотека,
    але коли телеметрія показує дивні числа, треба розуміти, що вона робить усередині.

13. Хіба зсуви не повільніші за reinterpret_cast?
    Ні. Компілятор розпізнає шаблон і робить з нього одну інструкцію. Перевірено, -O2, ARM64, clang і GCC 13 однаково:
        readU32Le (чотири зсуви)  →  ldr w0, [x0]              — одне читання
        readU32Be                 →  ldr w0, [x0]; rev w0, w0  — читання + перестановка байтів
    Тобто правильний код і швидкий. Писати UB заради швидкості не треба.

14. Навіщо контрольна сума на UART і чому XOR слабкий?
    UART не має власної перевірки цілісності (на відміну від Ethernet/TCP). Байти псуються через перешкоди
    від моторів і ESC, поганий контакт у роз'ємі, переповнення буфера (Linux не встиг прочитати — байт загубився).
    Контрольна сума — єдиний спосіб про це дізнатися.
    XOR (MSP v1) не залежить від порядку: 01 02 і 02 01 дають ту саму суму 0x03. Не бачить переставлених байтів
    і двох помилок в одному й тому самому біті різних байтів.
    Сума Флетчера (UBX): A += байт; B += A. B залежить від позиції байта:
        01 02 → A = 3, B = 4;   02 01 → A = 3, B = 5   — перестановку видно.
    CRC (MAVLink — CRC-16/MCRF4XX, MSP v2 — CRC-8) ще надійніший.
    Після контрольної суми все одно перевіряти довжину: заголовок обіцяє 4 ГБ → відкинути одразу
    (maxPayload із сесії 3), а не чекати й накопичувати.

15. Як тестувати код розбору бінарних даних?
    - Відомі байти → відоме число, включно з межами: 00 80 → -32768, FF 7F → 32767, 38 FF → -200.
      Саме такий тест ловить «написав big-endian замість little-endian» (моя помилка в День 22).
    - Round-trip: encode → decode дає те саме (EncodeFrame/FrameDecoder у сесії 3).
    - Кадр шматками: по одному байту, розірваний заголовок, сміття перед кадром, зіпсована контрольна сума.
    - Збірка з UBSan: ловить невирівняне читання й зсуви за межі типу; ASan — читання за межами буфера,
      коли довжина в заголовку більша за реальні дані.
    - Далі, якщо треба: fuzzing (libFuzzer) — мільйони випадкових входів у парсер, шукає падіння.
