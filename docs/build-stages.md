Етапи збірки: препроцесор, компілятор, лінкер
(Підсумок повторення R4, вправа sandbox/repeat/r4/build.sh. Усі приклади перевірено:
Mac clang ARM64 і Linux GCC 13, листопад 2026)

Коротка відповідь на співбесіді (30 секунд): «У вас undefined reference. Що це і що робите?»
    Це етап лінкування. Компілятор побачив оголошення і повірив йому, а лінкер не знайшов
    визначення з таким самим ім'ям у жодному .o чи бібліотеці. Причини: .cpp не доданий у збірку
    або бібліотека не підключена; сигнатура визначення не збігається з оголошенням (тип, const,
    namespace); C-функція без extern "C"; шаблон визначено в .cpp, а не в заголовку; визначення
    static або в анонімному namespace. Шукаю так: беру точне ім'я з помилки і через nm -C
    дивлюся, в якому .o є T з цим ім'ям і чим воно відрізняється.

0. Головне правило
    Кожна команда обробляє лише ті файли, які в ній перелічені. Кожен .cpp компілюється окремо
    (одиниця трансляції, translation unit) і про інші .cpp нічого не знає.
    У Gradle javac бачить увесь модуль одразу, а тут — ні.

        main.cpp    ─препроцесор─► текст ─компілятор─► main.o    ─┐
        battery.cpp ─препроцесор─► текст ─компілятор─► battery.o ─┼─лінкер─► app
                                          бібліотеки (libc, -l…) ─┘

1. Препроцесор
    Вхід: один .cpp. Вихід: один великий текст, у який уставлено всі заголовки.
    Працює лише з текстом: не розуміє ні функцій, ні типів.
    #include "battery.h" — знайти файл і вставити його текст на місце цього рядка.
        "…" шукає спершу поруч із .cpp, потім у теках з -I; <…> — у теках з -I і в системних.
    #define, #ifdef — підставити текст або викинути шматок коду (так -DNDEBUG вимикає assert).
    Подивитися результат: clang++ -E -Iinclude main.cpp
        main.cpp на 8 рядків після препроцесора займає понад 700 рядків: увесь <cstdio> уставлено текстом.
    Типова помилка: fatal error: 'battery.h' file not found (GCC: No such file or directory).
        «file not found» на рядку #include — це завжди препроцесор: не передали -I.

    Прапорці:
        -I<тека>          де шукати заголовки                      CMake: target_include_directories
        -D<ім'я>[=знач]   визначити макрос (-DNDEBUG вимикає assert) CMake: target_compile_definitions
        -E                зупинитися після препроцесора і надрукувати текст

2. Компілятор
    Вхід: текст одного .cpp після препроцесора. Вихід: об'єктний файл .o — машинний код лише цього .cpp.
    Щоб викликати функцію, йому досить оголошення (ім'я і типи параметрів), тіло не потрібне.
    Оголошення для нього — обіцянка: «десь буде визначення».
    Перевіряє синтаксис, типи і чи збігається виклик з оголошенням.
    У .o записує дві речі (видно через nm -C):
        T — функція визначена тут (тіло лежить у розділі .text: так історично називають машинний код)
        U — undefined: використовую, але в мені її немає, шукайте ззовні
    Типові помилки: too few arguments to function call, no matching function,
        use of undeclared identifier — виклик не збігається з оголошенням або оголошення немає.

    Підступ (випадок 6 вправи). Оголошено cellVoltage(float, int), а визначено
    cellVoltage(float, unsigned) — і це компілюється без помилок. Для C++ це дві різні функції
    з одним ім'ям, тобто перевантаження (як fun f(x: Int) і fun f(x: UInt) у Kotlin).
    Компілятор не може знати, що малося на увазі одне й те саме.

    Прапорці:
        -c                   лише скомпілювати в .o, лінкер не викликати
        -std=c++20           версія мови                                 CMake: CMAKE_CXX_STANDARD
        -O0 / -O2 / -O3      рівень оптимізації                          CMake: CMAKE_BUILD_TYPE
                             (Debug: -g без оптимізації; Release: -O3 -DNDEBUG; RelWithDebInfo: -O2 -g)
        -g                   додати налагоджувальну інформацію для gdb
        -Wall -Wextra        попередження                                CMake: target_compile_options
        -Werror              зробити попередження помилками
        -fsanitize=address   вбудувати перевірки ASan (потрібен і лінкеру, див. нижче)
        -S                   зупинитися на асемблері (.s): подивитися, що згенерував компілятор
        -o <файл>            куди записати результат (для будь-якого етапу)

3. Лінкер
    Вхід: усі .o і бібліотеки. Вихід: готова програма (або бібліотека .so).
    Для кожного U шукає T з точно таким самим ім'ям в інших .o і бібліотеках.
        не знайшов → undefined reference (Linux) / Undefined symbols for architecture arm64 (Mac)
        знайшов два → multiple definition (Linux) / duplicate symbol (Mac). Наприклад, функція
            визначена в заголовку без inline, а заголовок включено у два .cpp.
    Тексту і #include тут уже немає, лише машинний код. Тому -I лінкеру не потрібен.
    printf у main.o теж U: його T лежить у стандартній бібліотеці C, яку clang++ підключає сам.

    Ім'я з типами (name mangling). Типи параметрів закодовано прямо в імені символу:
        nm main.o               U _ZN5drone11cellVoltageEfi     f = float, i = int
        nm battery_unsigned.o   T _ZN5drone11cellVoltageEfj     j = unsigned int
        nm -C main.o            U drone::cellVoltage(float, int)   (-C розкодовує ім'я)
    На Mac перед іменем ще один символ _ (__ZN5drone…). Для лінкера це просто два різні рядки.
    Тому зміна типу параметра лише в .cpp — помилка лінкера, а не компілятора (випадок 7).
    У C імена не кодуються (функція crc8 так і називається crc8). Тому C-бібліотеку оголошують
    через extern "C", інакше C++ шукатиме закодоване ім'я, якого в бібліотеці немає.

    Прапорці:
        файли .o, .a           що зібрати разом
        -l<ім'я>               підключити бібліотеку lib<ім'я>.so або lib<ім'я>.a   CMake: target_link_libraries
        -L<тека>               де шукати бібліотеки для -l
        -fsanitize=address     підключити бібліотеку ASan. Якщо скомпілювати з ним, а лінкувати
                               без нього: Undefined symbols "___asan_init".
        -pthread               потоки (передавати і компілятору, і лінкеру)
        -Wl,<опція>            передати опцію напряму лінкеру

    Порядок на Linux (GNU ld) має значення: бібліотека -l… має стояти ПІСЛЯ файлів, які її використовують.
        g++ -L. -lbattery main.cpp -o app   → undefined reference
        g++ main.cpp -L. -lbattery -o app   → OK
    (Перевірено зі статичною libbattery.a. Лінкер на Mac на порядок не зважає: на Mac не помітите, а на Pi впаде.)

4. Аналогія з Android
    Компілюєте проти однієї версії бібліотеки, а запускаєте з іншою: код збирається, а на пристрої
    падає NoSuchMethodError. У Java метод шукають під час виконання. У C++ цю саму перевірку робить
    лінкер ще до запуску: undefined reference — це NoSuchMethodError на етапі збірки.

5. Причини undefined reference і як шукати
    1) .cpp не доданий у збірку (add_executable / add_library) або бібліотека не підключена
       (target_link_libraries) чи стоїть не в тому порядку.
    2) Сигнатура визначення не збігається з оголошенням: тип, const, namespace.
    3) C-функція підключена без extern "C".
    4) Шаблон визначено в .cpp, а не в заголовку.
    5) Визначення static або в анонімному namespace: у nm це маленька t, видно лише всередині свого .o.
    Як шукати: взяти точне ім'я з тексту помилки (там є і типи), потім
        nm -C *.o | grep cellVoltage
    і знайти, в якому .o є T і чим його ім'я відрізняється від потрібного U.
